# Akinal İnşaat — Full Pre-Refactor Audit
**Date:** 2026-06-24  
**Auditor:** Claude Code  
**Scope:** Read-only. No files modified. No SQL mutated. No commits made.

## Executive Summary

The project is a PHP/MySQL REST API + React/Vite SPA deployed on cPanel shared hosting. The backend is structurally sound but carries two critical security risks and a persistent financial data-source inconsistency that causes different screens to show different totals for the same customer. The test suite passes (36/36). Lint has 207 problems (191 errors, almost all `no-explicit-any`). TypeScript strict mode is disabled.

## 5. Security Findings

### CRITICAL

**C1 — Plaintext credentials in `config.php`**  
File: [public_html/api/config.php:14](../public_html/api/config.php#L14)  
`DB_PASS`, `VAPID_PRIVATE_KEY`, and `TURNSTILE_SECRET_KEY` are hardcoded in a committed file. The file comment says "Do not commit config.php" but the file is tracked in git.  
**Action needed:** Verify `.gitignore` excludes `config.php`. Rotate credentials if this has been pushed to any remote.

**C2 — SQL editor enabled in production**  
File: [public_html/api/config.php:24](../public_html/api/config.php#L24)  
`define('ENABLE_ADMIN_SQL_EDITOR', true)`  
File: [public_html/api/admin/sql-editor.php:40](../public_html/api/admin/sql-editor.php#L40)  
`$pdo->query($sql)` — raw SQL execution. A compromised admin session = full database access.  
**Action needed:** Set `ENABLE_ADMIN_SQL_EDITOR` to `false` on production server config.php. The code already gates on this constant (line 9), so the fix is one line.

### HIGH

**H1 — SQL injection in schema-migration guards (`customers.php`)**  
File: [public_html/api/admin/customers.php](../public_html/api/admin/customers.php)  
Lines 129, 149, 158, 163-164: Table names and column names interpolated into `db()->query()` and `db()->exec()`.  
These are schema migration guards (`ensure_account_type_columns`) that run on every POST/PATCH. The table names are hardcoded strings (not user input), so the practical injection risk is low — but it is architecturally wrong and any future refactor could introduce real injection.  
**Exact code:**
```php
$statement = db()->query("SHOW COLUMNS FROM `{$table}`");  // line 397 — table from parameter
db()->exec("ALTER TABLE {$table} ADD COLUMN account_type ... AFTER {$afterColumn}");  // line 163
```
**Action needed:** Replace these schema migration guards with a proper idempotent migration system. These ALTER TABLE calls on every request are also a performance risk.

**H2 — SQL injection in `login.php`**  
File: [public_html/api/admin/login.php:64](../public_html/api/admin/login.php#L64)  
`$pdo->query('SHOW COLUMNS FROM ' . $table)` — table name from a local variable, but the pattern is dangerous.

### MEDIUM

**M1 — Column list interpolation in `media.php`**  
File: `public_html/api/admin/media.php:175`  
`SELECT {$select} FROM ak_site_settings` — `$select` is assembled from `SHOW COLUMNS` output, not user input. Low real risk but wrong pattern.

**M2 — LIMIT interpolation in `notifications.php`**  
File: `public_html/api/admin/notifications.php:18`  
`LIMIT {$limit}` — `$limit` appears to be an integer cast from GET param. Low risk if cast is confirmed.

**M3 — `SUPABASE_DB_PASSWORD` in `.env.local`**  
File: `.env.local`  
Supabase is supposed to be legacy-only. This password should be removed and the credential rotated if it still grants access to any live system.

**M4 — TypeScript `strictNullChecks: false`**  
File: [tsconfig.app.json](../tsconfig.app.json)  
Null/undefined errors are invisible at compile time. Combined with heavy `any` usage (191 lint errors), runtime null crashes can slip through.

**M5 — Utility PHP files exposed in web root**  
`public_html/create-admin-user.php`, `public_html/install-schema.php`, `public_html/import-projects.php` — these should be removed or protected with IP restrictions on production.

## 7. Customer Module Detail

**`ak_customer_notes` status:**  
- `customers.php` still has active read (`SELECT * FROM ak_customer_notes WHERE customer_id = :id`) and write (`INSERT INTO ak_customer_notes`) paths.  
- `ak_customers.notes` column also exists and is set via `customer_payload()` on every create/update.  
- These are two parallel notes systems. The notes table supports multiple notes per customer; the column supports one editable note field.

**Customer type enforcement:**  
`customer_payload()` correctly normalizes `'Firma'` → `'Kurumsal'` and rejects anything else. Only `Bireysel` / `Kurumsal` are accepted. Customer `status` is still written (`'Aktif'` default) but not used as a business concept per confirmed decisions.

## 8. Canonical Read Model Status

The dashboard uses a **shadow-compare infrastructure** (`canonical-read-flags.php`). Key findings:

- `CANONICAL_READ_MODEL_ENABLED` defaults to `false` → **legacy calculation path is live** on all dashboard endpoints.
- Shadow comparison is active (`shadow_compare = true`), which means mismatches between legacy and canonical are logged to PHP error log but do not affect output.
- `CANONICAL_READ_MODEL_FAIL_CLOSED = true` → if the canonical model has missing required fields, it will not be used even if enabled.
- The new canonical model (`backend-canonical-read-model.php`) exists and is ready but not yet the source of truth.

## 11. Safe Next Steps (Post-Audit)

1. **Immediate (no code change required):** Set `ENABLE_ADMIN_SQL_EDITOR=false` in production `config.php`. One line.
2. **Verify git history:** Confirm `config.php` is in `.gitignore` and has never been pushed to any remote. If it has, rotate `DB_PASS`, `VAPID_PRIVATE_KEY`, and `TURNSTILE_SECRET_KEY`.
3. **Owner decisions (Q1–Q8):** Answer the 8 questions above before any refactor begins.
4. **Row counts on suspect tables:** Run `SELECT table_name, table_rows FROM information_schema.tables WHERE table_schema = 'akinalin_wp282'` and `SELECT MAX(created_at) FROM ak_expenses` to determine legacy table activity.
5. **Decide canonical financial source:** Once Q3 and Q5 are answered, the dual-source inconsistency in `AdminCustomers.tsx:66-68` and `dashboard.php` can be resolved in a single targeted change.
6. **Remove schema-migration guards:** `ensure_account_type_columns()` runs on every POST/PATCH to `customers.php` and issues ALTER TABLE if columns are missing. These columns now exist; the guards should be removed after confirming production schema.
